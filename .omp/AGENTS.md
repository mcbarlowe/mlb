# OMP repo notes

- Package manager: `uv`. Bootstrap with `uv sync --group dev`.
- Default database target: local PostgreSQL `dbname=postgres schema=mlb`. Override with `MLB_DB_NAME`, `MLB_DB_USER`, `MLB_DB_PASSWORD`, `MLB_DB_HOST`, `MLB_DB_PORT`, and `MLB_DB_SCHEMA`.
- Fast verification commands:
  - `uv run pytest -q test_game_dimensions.py test_game_pitches_relation.py test_postgres_backfill.py`
  - `uv run python verify_database.py`
  - `uv run ruff check mlb/database mlb/etl/get_live_feeds.py mlb/etl/load_to_database.py mlb/etl/postgres_backfill.py scripts/backfill_postgres.py examples/database_examples.py test_game_dimensions.py test_game_pitches_relation.py test_postgres_backfill.py verify_database.py`
  - `uv run basedpyright`
- `pyrightconfig.json` intentionally scopes type-checking to the PostgreSQL ETL surface so OMP diagnostics stay actionable.
- Resumable backfill command: `uv run python scripts/backfill_postgres.py` (downloads missing schedules/live feeds asynchronously, then resumes the Postgres backfill)
- Bulk historical mode: `uv run python scripts/backfill_postgres.py --bulk-historical` (batches inserts by season and skips any games already present in `mlb.games`; a season is skipped entirely once all of its game files are already loaded)
- MLflow training command: `uv run python scripts/train_models_with_mlflow.py` (defaults to shared MLflow HTTP server `http://10.0.0.171:5001` and experiment `mlb-model-training-shared`; pass `--mlflow-tracking-uri sqlite:///...` only for intentional local runs)
- Pitch type/location prediction model registration (predicts the thrown pitch, NOT its outcome — outcome models are the `mlb/outcome` Stage A/B registrations): `uv run python scripts/import_pitch_models_to_mlflow.py [--set-champion]` (registers the on-disk pitch type + location releases as `mlb-pitch-type-lstm-attention` / `mlb-pitch-type-conditioned-location` versions in shared MLflow under collection `pitch_type_prediction_models`; auto-resolution picks the newest complete non-quick `models/pitch_type/run_*` and newest complete `models/pitch_type_location/pitch_type_location_*`, override with `--pitch-type-run-dir`/`--location-run-dir`. Registered versions are pickle-serialized pytorch models — loading needs `MLFLOW_ALLOW_PICKLE_DESERIALIZATION=true` and `src.ml` importable)
- Training on a machine without Postgres (e.g. the MacBook Air): export per-season parquet on a DB host via `load_pitches_from_postgres(seasons=[s]).write_parquet("data/training_parquet/<season>/pitches.parquet")`, rsync `data/training_parquet/` across, then pass `--data-path data/training_parquet` to the training scripts. Export fresh from `mlb.pitches` (never reuse `data/processed/livefeeds` for training — it predates the 2026-08-09 base/out repair). Avoid `--low-memory` there: it reloads and re-transforms every season each epoch.
- BEFORE retraining any torch model that early-stops on validation metrics: review the stopping criterion. Both trainers (`PitchPredictionTrainer` in `mlb/ml/train.py` and `PitchTypeLocationTrainer` in `mlb/ml/pitch_type_location_model.py`) reset patience on a bare `val < best` with no minimum delta, so noise-level improvements extend training (owner flagged 2026-08-10: may capture variance, not true improvement). Planned fix shape: keep strict `<` for best-weight stashing, but require `val < best - min_delta` to reset patience. Calibration from the 2026-08-11 full location run (90 epochs, 10 of 23 best-events were <1e-3 nats): `min_delta=1e-3` would have stopped at epoch 56 for +0.0029 val NLL — use ~1e-3 as the starting value.
- Pitcher movement profiles (leak-free, as-of-game trailing usage/velo/pfx/spin per pitch type): rebuild with `uv run python scripts/build_pitcher_movement_profiles.py` (reads Postgres, writes `data/profiles/`; ~75s). Opt into the +55 features by constructing `PitchFeatureEngine(..., movement_profiles_dir="data/profiles")` — changes the model feature contract, so only enable together with a retrain. Live inference falls back to the pitcher's latest stored profile, so refresh the store daily when a profile-consuming model is deployed.
- Model serving is registry-driven: the live pitch pipeline (`run_live_pipeline.py`) and the sim slate both resolve MLflow `@champion` aliases at launch (`mlb/ml/mlflow_artifacts.py` / `mlb/outcome/mlflow_artifacts.py`), downloading versions into local caches (`models/mlflow_cache/`) with newest-cache fallback when the server is unreachable. Promoting a champion in MLflow is the ONLY step needed to change what serves; local run-dir resolution (`mlb/ml/run_dirs.py`) exists solely for the import script and explicit debug overrides (`--pitch-type-model <dir>`).
- Outcome model training: `uv run python scripts/train_outcome_models.py` (same MLflow default as above; `scripts/run_outcome_training.sh` is an optional convenience wrapper that resolves `MLFLOW_TRACKING_URI` from the current shell or `~/.zshrc`; `--quick` trains a 1-season smoke in ~4 minutes)
- Sample-data regression tests use `example_json_files/example_live_feed.json`; they do not require a populated `data/` tree.
- Treat `data/`, `models/`, `output/`, `catboost_info/`, and executed notebooks as local/generated artifacts unless the task explicitly targets them.
- ETL/database code lives in `mlb/endpoints`, `mlb/data`, `mlb/database`, and `mlb/etl`.
- ML training code lives in `mlb/ml` and `scripts/`; it depends on `torch` and `catboost` and is separate from the Postgres ETL path.
- Pitch outcome models live in `mlb/outcome` (Stage A/B CatBoost + leak-free dataset builder); deliberately independent of `mlb/ml` pitch prediction models — shared contract is pitch-type codes + plate coordinates only. Tests: `uv run pytest -q test_outcome_models.py`.
- Game simulation core lives in `mlb/sim` (count machine, empirical base-out tables, count-conditioned pitch mixes, PA + full-game Monte Carlo). Rebuild tables with `uv run python scripts/build_base_out_tables.py` (reads raw live feed JSONs under `data/raw/livefeeds/`, not Postgres) and `uv run python scripts/export_pitch_mix.py` (reads Postgres). Simulate: `uv run python scripts/simulate_game.py --game-pk <pk>` (archived game), `--slate [--date YYYY-MM-DD]` (today's unstarted games, probable pitchers + lineups projected from each team's last final), `--validate --season 2025 --games 30` (aggregate calibration). Tests: `uv run pytest -q test_sim_engine.py test_game_sim.py test_game_sim_card.py`.
- Evaluate win-prediction and outcome models on BOTH Brier score and log loss. Stage-level val/test log loss + Brier are logged to MLflow by `scripts/train_outcome_models.py`; game-level win Brier/log loss (with coin, league-home-rate, and always-home baselines) are logged by `simulate_game.py --validate` against the shared MLflow default unless a tracking URI override is passed.
- After any outcome-model, pitch-mix, or profile change: rerun `uv run python scripts/calibrate_sim.py` (per-side rate multipliers) and then `uv run python scripts/simulate_game.py --fit-win-calibration --season 2024` (anchored p(home) Platt; NEVER fit on 2025 — it is the test season). Both write under `models/sim/`.

- THE NON-PITCH-EVENT LOADER BUG (diagnosed and repaired 2026-09-05, `scripts/fix_pitches_non_pitch_events.py`). The legacy extraction walked `play["pitchIndex"]` and emitted a row for EVERY referenced `playEvents` entry, but `pitchIndex` also points at `isPitch: false` events — pickoff attempts, pitcher step-offs, and the "Automatic Ball/Strike" events from intentional walks and pitch-timer violations. Those events either carry no `pitchNumber` (so `pitch.get("pitchNumber", 0)` stored 0) or REUSE the preceding real pitch's `pitchNumber`; `pitches_pk` + `ON CONFLICT DO NOTHING` then collapsed the collisions, keeping whichever row COPY reached first. Two defects resulted: 238,769 junk rows parked at `pitch_number = 0`, and 2,340 REAL pitches evicted by an `Automatic %` event that stole their key (evicting the real pitch ~78% of the time). The extraction was fixed by commit `71533db` (2026-08-27) which skips `isPitch is not True`, so games loaded from 2026-08-25 onward are clean — verify with `select count(*) from mlb.pitches where pitch_number = 0` scoped to recent game_dates. The repair re-fetched 2,417 games from StatsAPI and rewrote their pitch rows; all 2,340 evicted pitches are restored (`... where pitch_number > 0 and pitch_call_description like 'Automatic %'` is now 0). Detector for future regressions is in the script's `TARGET_SQL`: pitch rows stopping before the linescore's last inning, `at_bat_index` gaps, final games with no pitches, or `Automatic %` rows at `pitch_number > 0`. NOTE: after the fix, `at_bat_index` gaps are EXPECTED and benign — an at-bat can legitimately contain no pitches (intentional walk, runner caught stealing), so gaps alone are not a defect; 28 still-flagged games were verified pitch-for-pitch against StatsAPI with zero delta.
- RESOLVED 2026-09-05: the 225,619 leftover junk `pitch_number = 0` rows were deleted with `uv run python scripts/fix_pitches_non_pitch_events.py --purge-non-pitch-rows` (safety-gated: it refuses to run if any row at 0 carries tracking data or an unexpected description, then `VACUUM (ANALYZE) mlb.pitches`). `mlb.pitches` went 14,271,863 -> 14,046,244 rows and every row now represents a real pitch, so pitch counts and per-pitch rates off the table are correct. `data/livefeed_pk_collisions.parquet` (70,960 rows, full 78-column schema) is retained as the only local copy of the collision groups; the pickoff/step-off events it holds are real baseball events and would need an `mlb.play_events` table to live in the DB. Any non-pitch event is otherwise re-derivable from the public StatsAPI feeds, which serve 2009-era games fine.
