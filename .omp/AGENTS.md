# OMP repo notes

- Package manager: `uv`. Bootstrap with `uv sync --group dev`.
- Default database target: local PostgreSQL `dbname=postgres schema=mlb`. Override with `MLB_DB_NAME`, `MLB_DB_USER`, `MLB_DB_PASSWORD`, `MLB_DB_HOST`, `MLB_DB_PORT`, and `MLB_DB_SCHEMA`.
- Fast verification commands:
  - `uv run pytest -q test_game_dimensions.py test_game_pitches_relation.py test_postgres_backfill.py`
  - `uv run python verify_database.py`
  - `uv run ruff check src/database src/etl/get_live_feeds.py src/etl/load_to_database.py src/etl/postgres_backfill.py scripts/backfill_postgres.py examples/database_examples.py test_game_dimensions.py test_game_pitches_relation.py test_postgres_backfill.py verify_database.py`
  - `uv run basedpyright`
- `pyrightconfig.json` intentionally scopes type-checking to the PostgreSQL ETL surface so OMP diagnostics stay actionable.
- Resumable backfill command: `uv run python scripts/backfill_postgres.py` (downloads missing schedules/live feeds asynchronously, then resumes the Postgres backfill)
- Bulk historical mode: `uv run python scripts/backfill_postgres.py --bulk-historical` (batches inserts by season and skips any games already present in `mlb.games`; a season is skipped entirely once all of its game files are already loaded)
- MLflow training command: `uv run python scripts/train_models_with_mlflow.py` (defaults to shared MLflow HTTP server `http://10.0.0.171:5001` and experiment `mlb-model-training-shared`; pass `--mlflow-tracking-uri sqlite:///...` only for intentional local runs)
- Pitch type/location prediction model registration (predicts the thrown pitch, NOT its outcome — outcome models are the `src/outcome` Stage A/B registrations): `uv run python scripts/import_pitch_models_to_mlflow.py [--set-champion]` (registers the on-disk pitch type + location releases as `mlb-pitch-type-lstm-attention` / `mlb-pitch-type-conditioned-location` versions in shared MLflow under collection `pitch_type_prediction_models`; auto-resolution picks the newest complete non-quick `models/pitch_type/run_*` and newest complete `models/pitch_type_location/pitch_type_location_*`, override with `--pitch-type-run-dir`/`--location-run-dir`. Registered versions are pickle-serialized pytorch models — loading needs `MLFLOW_ALLOW_PICKLE_DESERIALIZATION=true` and `src.ml` importable)
- Training on a machine without Postgres (e.g. the MacBook Air): export per-season parquet on a DB host via `load_pitches_from_postgres(seasons=[s]).write_parquet("data/training_parquet/<season>/pitches.parquet")`, rsync `data/training_parquet/` across, then pass `--data-path data/training_parquet` to the training scripts. Export fresh from `mlb.pitches` (never reuse `data/processed/livefeeds` for training — it predates the 2026-08-09 base/out repair). Avoid `--low-memory` there: it reloads and re-transforms every season each epoch.
- BEFORE retraining any torch model that early-stops on validation metrics: review the stopping criterion. Both trainers (`PitchPredictionTrainer` in `src/ml/train.py` and `PitchTypeLocationTrainer` in `src/ml/pitch_type_location_model.py`) reset patience on a bare `val < best` with no minimum delta, so noise-level improvements extend training (owner flagged 2026-08-10: may capture variance, not true improvement). Planned fix shape: keep strict `<` for best-weight stashing, but require `val < best - min_delta` to reset patience. Calibration from the 2026-08-11 full location run (90 epochs, 10 of 23 best-events were <1e-3 nats): `min_delta=1e-3` would have stopped at epoch 56 for +0.0029 val NLL — use ~1e-3 as the starting value.
- Pitcher movement profiles (leak-free, as-of-game trailing usage/velo/pfx/spin per pitch type): rebuild with `uv run python scripts/build_pitcher_movement_profiles.py` (reads Postgres, writes `data/profiles/`; ~75s). Opt into the +55 features by constructing `PitchFeatureEngine(..., movement_profiles_dir="data/profiles")` — changes the model feature contract, so only enable together with a retrain. Live inference falls back to the pitcher's latest stored profile, so refresh the store daily when a profile-consuming model is deployed.
- Model serving is registry-driven: the live pitch pipeline (`run_live_pipeline.py`) and the sim slate both resolve MLflow `@champion` aliases at launch (`src/ml/mlflow_artifacts.py` / `src/outcome/mlflow_artifacts.py`), downloading versions into local caches (`models/mlflow_cache/`) with newest-cache fallback when the server is unreachable. Promoting a champion in MLflow is the ONLY step needed to change what serves; local run-dir resolution (`src/ml/run_dirs.py`) exists solely for the import script and explicit debug overrides (`--pitch-type-model <dir>`).
- Outcome model training: `uv run python scripts/train_outcome_models.py` (same MLflow default as above; `scripts/run_outcome_training.sh` is an optional convenience wrapper that resolves `MLFLOW_TRACKING_URI` from the current shell or `~/.zshrc`; `--quick` trains a 1-season smoke in ~4 minutes)
- Sample-data regression tests use `example_json_files/example_live_feed.json`; they do not require a populated `data/` tree.
- Treat `data/`, `models/`, `output/`, `catboost_info/`, and executed notebooks as local/generated artifacts unless the task explicitly targets them.
- ETL/database code lives in `src/endpoints`, `src/data`, `src/database`, and `src/etl`.
- ML training code lives in `src/ml` and `scripts/`; it depends on `torch` and `catboost` and is separate from the Postgres ETL path.
- Pitch outcome models live in `src/outcome` (Stage A/B CatBoost + leak-free dataset builder); deliberately independent of `src/ml` pitch prediction models — shared contract is pitch-type codes + plate coordinates only. Tests: `uv run pytest -q test_outcome_models.py`.
- Game simulation core lives in `src/sim` (count machine, empirical base-out tables, count-conditioned pitch mixes, PA + full-game Monte Carlo). Rebuild tables with `uv run python scripts/build_base_out_tables.py` (reads raw live feed JSONs under `data/raw/livefeeds/`, not Postgres) and `uv run python scripts/export_pitch_mix.py` (reads Postgres). Simulate: `uv run python scripts/simulate_game.py --game-pk <pk>` (archived game), `--slate [--date YYYY-MM-DD]` (today's unstarted games, probable pitchers + lineups projected from each team's last final), `--validate --season 2025 --games 30` (aggregate calibration). Tests: `uv run pytest -q test_sim_engine.py test_game_sim.py test_game_sim_card.py`.
- Evaluate win-prediction and outcome models on BOTH Brier score and log loss. Stage-level val/test log loss + Brier are logged to MLflow by `scripts/train_outcome_models.py`; game-level win Brier/log loss (with coin, league-home-rate, and always-home baselines) are logged by `simulate_game.py --validate` against the shared MLflow default unless a tracking URI override is passed.
- After any outcome-model, pitch-mix, or profile change: rerun `uv run python scripts/calibrate_sim.py` (per-side rate multipliers) and then `uv run python scripts/simulate_game.py --fit-win-calibration --season 2024` (anchored p(home) Platt; NEVER fit on 2025 — it is the test season). Both write under `models/sim/`.
- Batter prop shopping: `ODDS_API_KEY=... uv run python scripts/shop_batter_props.py [--player <substr>] [--markets ...] [--show-all]` — live per-book prices for HR/hits/TB/RBI/runs/BB/SB props (Over AND Under, per line) with best price/book, consensus, no-vig fair prob, DB 3yr/1yr/L30 rates, and EV at the ADJUSTED rate: trailing 3-season rate -> exponential recency decay (`--recency-half-life 400` games) -> aging projection on log-odds (`models/props/aging_curves.json`, rebuild with `uv run python scripts/build_prop_aging_curves.py`) -> EB shrink toward board-pool league rate (`--shrink-k 50`) -> for all markets EXCEPT batter_home_runs: starts-only stream (PA>=3), expected-PA rescale on 0.5 lines (trailing-30-starts mean PA), and tonight's-park logit offset (`models/props/park_factors.json`, rebuild with `uv run python scripts/build_prop_park_factors.py`). Conditioning calibrated leak-free on 2024+2025: fixes hits-family under-side composition bias (realized/est 0.86 -> 0.93-1.00); HR provably does not benefit and stays unconditioned. Alert gates on adjusted EV: >=11% global, >=15% HR, >=150 stream GP, PLUS market anchors (two-sided fair prob required; ours <=1.5x and <=+15pp vs fair; price <= +1400; EV <= 50%). Runs on the iMac 4x daily (9:30/12/15/18 ET) as LaunchAgent `com.barloweanalytics.prop-shop` (runner `scripts/run_prop_shop.sh`, settles the ledger each pass), alerting via instant ntfy.sh push (topic `barlowe-props-c47d9e2a51b3`) and iMessage, deduped per day, re-alerts on >=3pp EV improvement. Env knobs `BARLOWE_PROP_SHOP_{MIN_EV,MIN_GP,MARKETS,MARKET_MIN_EV,SHRINK_K,HALF_LIFE,NOTIFY_METHOD,NTFY_TOPIC,START_HOUR,END_HOUR,RECIPIENT}`. Cost ~50-210 credits/run.
- Prop paper ledger: every texted prop alert is also logged as a flat-1u open bet in `mlb.prop_paper_bets` (PK alert_date+player+market+point+side; alerted best price/book, adjusted prob, EV, strategy_version). `uv run python scripts/settle_prop_alerts.py [--push]` settles open bets against `mlb.batting` (over wins on stat > point, under on stat < point, DNP -> void with stake returned) and prints the full ledger + all-time ROI; `run_prop_shop.sh` runs it after every shop pass, so the 9:30 ET run settles yesterday's card and pushes a "MLB Props P&L" ntfy summary automatically. The moneyline paper ledger (`mlb.paper_trades`) is separate and h2h-shaped — do not mix props into it.
- Prop estimator MLflow provenance + serving: the registry model `mlb-prop-rate-estimator` (collection `prop_models`, experiment `mlb-prop-models` on the shared server) holds one version per estimator generation (v1 raw+shrink, v2 +decay+aging+market-gates, v3 +conditioning = `@champion`), each with params, leak-free 2024+2025 calibration metrics + gate-price ROI, and the curve/park artifacts. Version tags carry `strategy_version` matching `mlb.prop_paper_bets` for live P&L joins. Serving is registry-driven: `shop_batter_props.py` resolves `@champion` at launch (`--model-source registry`, default) and uses its REGISTERED curve/park artifacts via a per-version cache (`models/mlflow_cache/prop_rate_estimator/v<N>/`) with newest-cache fallback when the server is unreachable and repo-local fallback otherwise; a champion whose `strategy_version` differs from the code's `STRATEGY_VERSION` is refused (warns, uses repo-local) since the estimator logic lives in code. After ANY estimator change: bump `STRATEGY_VERSION` in shop_batter_props.py, add a spec to `scripts/register_prop_model_mlflow.py`, run `uv run python scripts/register_prop_model_mlflow.py --set-champion` (idempotent). Calibration lives in `scripts/calibrate_prop_estimator.py`.
- Sim/prediction card posts: production captions must NOT describe model internals (plain matchup/result text only); the labels on the card graphic itself are approved as designed. Test posts stay prefixed `TEST GRAPHIC` and get deleted after review.
- The pitches table's base/out state was repaired in place on 2026-08-09 (`scripts/fix_pitches_base_state.py`, all 14.2M rows: true at-bat-start `outs` + runner flags/ids reconstructed from raw feeds); `outs` and `runner_on_*` are back in the outcome feature set. Rerun the repair after any bulk backfill that inserts games loaded with pre-fix code.
- The pitches table's spin columns were repaired in place on 2026-08-11 (`scripts/fix_pitches_spin.py`, 13.9M rows: the extraction read `pitchData.spinRate` instead of `pitchData.breaks.spinRate`, so `spin_rate` was always NULL and `spin_direction` was the literal string 'None'; both re-extracted from raw feeds, leftover 'None' strings scrubbed to NULL). Extraction fixed in `src/data/game_feed_data.py`. Rerun the repair after any bulk backfill of games loaded with pre-fix code. CAVEAT: spin values are PitchFX-inferred through 2016 (~1,730 rpm league avg) and Statcast-measured from 2017 (~2,250 rpm) — not comparable across that boundary.
- Barlowe2025 (MacBook Pro) training rules: ONE training job at a time — concurrent model training drains the machine to the point of instability. Before launching ANY training there: (1) get explicit owner approval for the window, (2) verify nothing is already training (`pgrep -f "train_"` over SSH must be empty). The iMac is the fallback for CPU-bound jobs.
